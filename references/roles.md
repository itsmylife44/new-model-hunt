# Roles

Every agent is a cold start: it has not seen the conversation, only its prompt.
Each prompt therefore names the repo, the notes to read first, the files it owns,
the JSON shape to return, and the one file under the run dir it may write. The
exact wording is generated by `scripts/hunt.py`; this file says what each role
is for and the bar it is held to, so the orchestrator can judge the output.

## Correctness hunter — one per subsystem, one per lens

Hunts bugs, not style: a result that is wrong, an off-by-one, truncation, an
inverted condition, a lost update, a race narrated as an interleaving, a leak
or double release traced on a path, unbounded growth, a string or path that
breaks on real input (unicode, spaces, a trimmed fragment, a very long line),
a shell script whose quoting or exit status fails on a real path, a Makefile
prerequisite that lies — and anything the notes promise that the code does not
keep.

Bar: every finding names a valid input or a concrete sequence that reaches an
observable wrong outcome, quotes the decisive lines with `file:line`, and
proposes the *smallest* edit. "Could go wrong if…" is not a finding. Malicious
peers, lying kernels, and hardening are out of scope; the untrusted boundary is
whatever this repo actually takes from outside (a socket, a file, a shell, a
PTY) and the wire between the repo's own programs.
Typically 2–8 real findings per hunt; zero is fine.

Output: `{"findings":[{file, line, title, evidence, failure, fix}]}`.

### The three lenses

A lens reads across subsystems for one shape of defect. The focus paragraph in
`run.json` must be rewritten for the repo at hand; these are the questions:

- **wire-contract** — for every request, reply, and event that crosses a
  process or module boundary: do the keys, types, and optionality each sender
  writes match what the receiver reads; do the several clients agree with each
  other; does the codec cover every type the protocol actually uses; do size
  limits on the two sides agree.
- **concurrency** — for each piece of mutable state, which queue/actor owns it
  and is every reader and writer on it; callbacks on the wrong queue; a lock
  held across an await or a blocking call; a source cancelled without closing
  its descriptor or a descriptor closed under a live source; re-entrancy into
  an object mid-update; ordering assumptions between two queues; a weak self
  that is nil exactly when it must not be. Report only races with a concrete
  interleaving.
- **lifecycle** — for each resource (descriptors, PTYs, children, sources,
  connections, observers, timers, files on disk, activities): where it is
  acquired and every path that releases it, including errors and early
  returns; a child reaped twice or never; an observer added per attach and
  never removed; a buffer that grows past the bound the notes promise.

## Clarity reviewer — one per subsystem

Applies the code-clarity method (`code-clarity/SKILL.md` under `~/.grok/skills/`,
`~/.claude/skills/`, or `~/.cursor/skills/` when installed; the prompt
summarises its gates otherwise) and the strict maintainability review's one
useful question — *is there a code-judo move that makes whole branches, flags,
or layers disappear while behaviour stays?* — under one constraint: the answer
must **remove** concepts.

Verdicts: `Bug` (a correctness defect found on the way — same bar as the
hunter), `Delete`, `Derive`, `Fold`, `Simplify`. There is no `Restructure`
verdict: a proposal that introduces a protocol, an actor, a manager, a
wrapper, a mode, or a new file to hold the same logic is not a clarity gain and
the skeptic refutes it.

Not reported: defensive checks to add, style (wrapping, labels, MARKs), naming
taste without a lying name, "could be a protocol" speculation, anything the
notes justify. Existing guards for scenarios that cannot occur *are* reported.
Typically 3–10 findings per subsystem, ranked by what a senior maintainer would
act on.

Output: `{"findings":[{file, line, verdict, title, evidence, behavior, change}]}`.

## Skeptic — one per hunt, both tracks

Job: refute. Default `refuted=true`. One skeptic takes the findings of one
hunt, reads the notes and that subsystem's sources once, then judges each
finding on its own and writes it its own verdict file; the findings do not
support each other, and the last one gets the reading the first one got.
`--solo` puts one skeptic on each finding instead, at one cold read per
finding. Either way the skeptic reads the notes (a documented gotcha or
platform constraint refutes unless the reviewer showed the note no longer
applies), reads the whole enclosing function and type (does the snippet exist
and behave as claimed), traces the failure or greps every symbol claimed
unused, checks whether an existing test already covers the path, and checks
whether the proposed fix over-guards or adds a concept.

`refuted=false` only when the skeptic can narrate the failure end to end (or,
for a clarity verdict, confirm no supported behaviour changes and the change
removes rather than adds). If the finding stands but is misstated or anchored
to the wrong place, `refuted=false` with a `corrected_title` — the corrected
title is authoritative downstream. If the defect is real but the hunter's fix
is wrong, `refuted=false` and the `reason` names the minimal fix; the patcher
follows the skeptic.

Severity (correctness): high = data loss, hang, crash, or a wrong result a user
will hit; medium = wrong result on a plausible but uncommon path; low = latent,
needs an unusual input. Severity (clarity): high = a real correctness risk;
medium = a concept a maintainer must understand that earns nothing; low = local
tidy-up.

Output: `{refuted, reason, severity, corrected_title}`.

## Patcher — one per disjoint file group

Reads the notes, then the real code (line numbers in the findings drift).
Edits only the files in its group, surgically; never rewrites a file; never
runs a git command that changes state; never builds into the repo; may compile
into `/tmp` the way the repo's harness target does. Follows the skeptic where
the skeptic corrected the hunter. Adds a test in the repo's own harness where
the header asks. Does not add narrating comments; matches the repo's comment
style. Reports one line per finding (`file:line — what changed`), then what it
could not do and why, then any change needed outside its group.

## Orchestrator

Carves, launches, joins, reports, asks once (what to patch), then groups,
launches patchers, builds, tests three times, commits by pathspec in the
repo's style, updates the notes when behaviour they describe changed, runs the
UI-copy skill, and releases only when told. Reads every diff before committing
it. Never reviews or patches code in the parent session except trivially
scoped scripts and the cross-group edits a patcher reported.
